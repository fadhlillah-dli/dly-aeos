DLY AEOS (DLY AI Engineering Operating System) is a local-first control plane for AI-assisted
software engineering. It runs on your own Windows or macOS machine from a clone of this repository,
serves one dashboard on `http://127.0.0.1:8787` and keeps humans in charge. This release contains
pull requests #1 to #11. The per-area list of changes is in the
[changelog](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/CHANGELOG.md).

Nothing in this release claims a capability works unless the Readiness Doctor or a recorded test
proves it. Evidence levels E0-E4 follow
[ADR-0061](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/docs/decisions/ADR-0061-evidence-ledger-levels.md).
Anything still unproven is listed below under "Known limitations and NOT-PROVEN".

## Highlights

- **Domain first, humans in charge.** You choose PERSONAL or OFFICE before any prompt, and no model
  can change that choice. Plan approval, publication, merge to `main` and production are human
  `Decision` records. Each one is bound to an exact target and content hash. Agent output is data,
  never approval.
- **Planning through the official Claude Code client.** The four-stage pipeline (Opus plans, Fable
  reviews) uses your native Max login: never the Claude API, never `--bare`, never
  `ANTHROPIC_API_KEY`. The first DLY AEOS plan was produced by DLY AEOS itself in a real run on the
  owner's Windows machine. It ended in `READY_FOR_HUMAN_REVIEW` (E3, that machine only; see
  [docs/evidence/first-plan](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/docs/evidence/first-plan/README.md)).
  Owner approval, publication and worker execution were not part of that run.
- **Evidence decides acceptance.** The independent verifier, evidence ledger, checkpoint review and
  delivery gates G0-G8 decide whether work is accepted. Worker exit 0 means REVIEW, not DONE, and
  UNKNOWN is never shown as a pass. The §50 acceptance suite maps all 82 rows: 77 PASS and 5
  PASS+BLOCKED (they need Docker, a real GitHub repository, an Atlassian tenant or a deployment
  target).
- **Container sandbox boundary on the build host.** Docker Desktop on Windows 11.
  `aeos worker containment --kind container` passed 20/20 checks for both the PERSONAL and the OFFICE
  profile (E3, that host only; see
  [docs/evidence/containment](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/docs/evidence/containment/README.md)).
- **OFFICE delivery built, off by default.** Bitbucket Cloud push and draft PR go through the broker,
  plus a Pipelines reader and Confluence/Jira adapters. All of it waits behind the interlock and a
  recorded company authorisation. A live tenant is NOT-PROVEN.
- **Operations.** Backup and restore test, release promotion and rollback, SLIs and alerts,
  incident records, an emergency stop, and
  [runbooks](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/docs/runbooks/README.md).
- **CI on the owner's hosts.** The backend suite and the bootstrap run on Windows, macOS on Apple
  Silicon and macOS on Intel. The frontend, real-browser and supply-chain jobs check
  platform-neutral artifacts.

## Supported hosts

| Host | Status | What proves it |
|---|---|---|
| Windows (PowerShell 5.1 or 7; Command Prompt through `aeos.cmd`) | supported | CI `windows-latest`: backend suite and bootstrap. Doctor sample and container containment on the owner's Windows 11 build host (E3). |
| macOS on Apple Silicon (arm64) | supported (CI only) | CI `macos-latest`: backend suite, bootstrap, mypy for darwin and win32, and the real trusted-suite verifier test. No run on a physical Mac is recorded. |
| macOS on Intel (x86_64) | supported (CI only) | CI `macos-26-intel`: backend suite and bootstrap. No run on a physical Mac is recorded. |
| Linux | not supported | The code paths remain, but no CI host job runs them (NOT-PROVEN). |

Requirements: Python 3.11 or newer (CI uses 3.13) and Git. Node.js 20 or newer builds the Control
Center (CI uses 24).

## Install

Follow the quick start in the
[README](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/README.md#quick-start). The full
guides are [docs/SETUP_WINDOWS.md](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/docs/SETUP_WINDOWS.md)
and [docs/SETUP_MACOS.md](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/docs/SETUP_MACOS.md).
The bootstrap scripts never install system software silently. They report what is missing and how
to install it with the official command. They also back up existing data before any migration and
install the pinned, universal `requirements.lock`.

The software is source-available for viewing only (see "Licence" below). The install steps are for
the copyright holder and for anyone with the holder's written permission.

## What needs owner setup

These steps cannot be automated and must not be. The dashboard and `aeos doctor` show which ones
are missing. Details are in the
[README](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/README.md#manual-steps-only-the-owner-can-do):

1. Create the first admin with `aeos admin create`. No default credentials exist.
2. Sign in to the official Claude Code client. `claude auth status` must show a claude.ai login,
   and `ANTHROPIC_API_KEY` must not be set.
3. Put the worker route key into the secret store with `aeos secrets set workers/openrouter`.
   It never goes in a file.
4. Install, initialise and unseal OpenBao with `aeos vault ...`. Keep the unseal keys offline.
5. For PERSONAL docs, create a Google OAuth client and give consent with
   `aeos publish google-connect`.
6. Store a fine-grained GitHub token limited to this repository with
   `aeos secrets set personal/github`.
7. Activate a worker model route and any budget. Each is your explicit decision in *Model & Rute*.
8. Optional: install Docker Desktop for container sandboxes.
9. Back up and run a restore test after the first real work.
10. OFFICE stays disabled until your company authorises routes, data classes and targets.

## Known limitations and NOT-PROVEN

Each item below is either NOT-PROVEN (no real run shows it yet) or a limit stated on purpose:

- **Worker execution.** No real OpenCode worker run exists: OpenCode is not installed on the build
  host. `CAN_RUN_WORKER` stays BLOCKED until the Doctor passes. The process sandbox without Docker
  is WEAK.
- **Verifier.** The verifier container runner has not run on a real candidate. Its npm, vitest,
  tsc and vite steps and the per-candidate `pip install` run outside a kill group
  ([ADR-0120](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/docs/decisions/ADR-0120-verifier-impact-selected-steps.md)).
- **macOS.** macOS is proven by CI runners only (backend suite and bootstrap on Apple Silicon and
  Intel). No interactive run on a physical Mac (dashboard, native Claude Code login, Doctor) is
  recorded, and Docker on macOS is NOT-PROVEN. The container boundary is proven only on the
  Windows 11 build host.
- **External writes.** Publication to Google Drive/Docs, GitHub Issues and pull requests on the
  real repository through DLY AEOS, and OpenRouter calls are all NOT-PROVEN. They need the owner's
  credentials and consent.
- **OFFICE.** The Bitbucket, Confluence and Jira adapters are disabled by default. A live tenant is
  NOT-PROVEN, and the work is blocked on company authorisation (milestone M5). The Bitbucket
  merge-check entitlement is reported as NOT_ENFORCEABLE.
- **Delivery.** A ruleset protects `main`, but a provider bypass test against it is NOT-PROVEN.
  No deployment target is configured, so the G6/G8 gates have not run against a live deployment.
- **Evaluation.** Eval runs on real routes and repeated experiments are NOT-PROVEN. Comparator and
  local evaluation are design only and cannot execute yet.
- **Supply chain.** SBOM, licence, vulnerability and SAST reports are REPORT_ONLY (`[NO-GATE]`)
  until the owner decides the thresholds in `policy/supply-chain.yaml`.
- **MCI.** Alignment stays UNVERIFIED until the canonical source can be read (master §51).
- **Linux.** It is not a tested host.
- **Docs visuals.** Product 1 Mermaid visuals stay VISUAL_PENDING when mermaid-cli is not
  installed.
- **Test isolation.** PR #11 named two fragile tests for the next round: an OAuth fixture computes
  its expiry at import time, and one scheduler test depends on test order.

Each capability's live status is shown by `aeos doctor` and the *Kesiapan (Doctor)* page. The
coverage matrix is
[docs/IMPLEMENTATION_COVERAGE.md](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/docs/IMPLEMENTATION_COVERAGE.md).

## Upgrade notes

This is the first release, so no earlier release exists to upgrade from. If you already have a
data directory from a build of `main` before this tag, do these steps in order:

1. **Back up first.** Run `aeos ops backup create --label before-v0.1.0`, then
   `aeos ops backup restore-test <backup_id>`. A backup is ready only after its restore test passes
   ([runbook](https://github.com/fadhlillah-dli/dly-aeos/blob/v0.1.0/docs/runbooks/backup-restore.md)).
2. **Update the checkout** to the `v0.1.0` tag and reinstall the pinned dependencies. Re-running
   `scripts/bootstrap.ps1` or `scripts/bootstrap.sh` does this. It also takes its own pre-bootstrap
   backup and runs the migrations.
3. **Migrate.** If you did not re-run the bootstrap, run `aeos db upgrade`, which takes a
   pre-upgrade backup first. Then check that `aeos db status` shows `current` equal to `head`. The
   migration chain is linear with one head.
4. **Check.** Run `aeos doctor`, then `aeos serve`.

Runtime data never lives in the repository. On Windows it is in `%LOCALAPPDATA%\DLY-AEOS`. On macOS
it is in `~/Library/Application Support/DLY-AEOS`.
