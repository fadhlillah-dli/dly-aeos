### Fixed

- **A route whose worker key is not stored is no longer eligible.** On 2026-10-28 two OpenCode Zen TRIAL routes named `workers/opencode-zen`, which was never stored. Routing checked only the namespace of `mode_params.credential_ref`, so both stayed eligible: Doctor `route.worker_key` reported MISSING (HIGH) and `CAN_RUN_WORKER` fell to BLOCKED although the OpenRouter route had its key, and a dispatcher could pick a keyless route and fail at call time. Routing now also requires the reference the broker would use (the route's own, or the default OpenRouter worker keys) to be PRESENT in the secret store, with the reason `credential <ref> not stored: aeos secrets set <ref>`; a sealed, unreachable or unknown store rejects every keyed route (fail closed). It is a status lookup (never a value, never a provider call), done only for a route nothing else rejects and at most once per reference per eligibility call. Loopback LOCAL and `claude-native` routes are unchanged. `route.registry` names the active routes kept out ("Dikecualikan: kunci belum disimpan"); `route.worker_key` judges the eligible routes and lists the keyless ones as a non-blocking note with both remedies (store the key, or disable the route), and stays MISSING when no eligible route is left. With no eligible route, `route.registry` names the real cause: a sealed, unreachable or unknown secret store gives UNKNOWN `SECRET_STORE_UNAVAILABLE` with the remedy to restore the store, and active routes kept out only for a missing key give the remedy to store the key or disable the route, neither a new (possibly paid) activation; storing a `workers/*` or `personal/openrouter` key now also marks `route.registry` STALE. Route activation and disable emit `route.activated` / `route.disabled` once from the routing service, so the CLI (which emitted nothing) and the API record the same event. Bite tests: keyed plus keyless TRIAL routes (only the keyed one eligible, worker readiness READY), all keyless (MISSING, store-the-key remedy), a sealed or absent store (fail closed, the store named as the cause), one event per CLI and API activation; near misses: loopback and `claude-native` routes need no key, storing the key makes the route eligible. A route check taken while the secret store was down no longer keeps that result for its one-hour lifetime: `aeos vault start`, `aeos vault stop` (OpenBao restarts sealed) and an unseal (from the OS keyring, also the auto-unseal of `aeos serve`, or from the hidden prompt) signal `secret:store` through `aeos.secrets.readiness.store_state_changed`, and `route.registry` and `route.worker_key` now declare it, so both turn STALE and are re-checked; before, nothing on these paths signalled `secret:store`. `aeos routes set-pool` and `aeos routes set-endpoint` now emit `route.pool_set` / `route.endpoint_set` once from the routing service, as the API did, so an open Models page refreshes after a CLI change too (owner request R28). Bite tests: store-down route results turn STALE after an unseal, each of start, stop and the prompted unseal sends exactly one signal, one event per CLI and API pool or endpoint change; near misses: an already unsealed vault, another credential's signal and a stop with nothing running leave the route results alone, a refused pool move emits nothing.
