### Added

- **Merge policy as code.** `.github/repository-settings.json`, `.github/rulesets/main.json` and `.github/rulesets/release-tags.json` hold the repository settings: a merge commit is the only merge method (squash and rebase off), head branches are deleted on merge, `commit subjects [G1]` and `pr title [G1]` become required checks next to the eight existing ones (branches need not be up to date, to avoid re-running the macOS jobs of every open pull request), and release tags `v*` cannot be deleted or force-updated. New `scripts/github_settings.py --check` compares the live settings with the files and ends with `GITHUB_SETTINGS: OK`, `DRIFT` or `ERROR`; `--apply --yes` writes them (never in CI, never deletes a ruleset, nothing changes without `--yes`). `REQUIRED_CHECKS` in `tests/unit/test_ci_gates.py` must equal the ruleset file and each name must be reported by exactly one job of all workflows. ADR-0115 has a dated amendment with the reasons and `CONTRIBUTING.md` "Merging" the procedure (`gh pr merge <n> --merge`, `--apply --yes` then `--check`). Evidence: E2 unit tests on macOS arm64 against a fake API (squash allowed and a missing context are each DRIFT naming `allowed_merge_methods` or the context, the identical state and reordered lists are OK, `--apply` without `--yes` sends nothing). NOT-PROVEN: the live `--apply` and a following `--check` of OK (the files were not applied to GitHub), and everything on Windows and macOS Intel until CI runs it.
